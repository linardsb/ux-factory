Approach · how I work

I design the interface and build the system behind it.

I'm a design engineer. Designers decide what a thing should be; engineers make it real. The expensive mistakes happen in the gap between those two jobs, so that gap is where I work: close enough to design to shape what gets built, close enough to the code to ship it.

The method The case study

The method

Four habits, run as one loop.

I run all four on every piece of work, and I go back to check whether the last one actually worked.

How I decide and pace work

Shape it

A vague ask becomes a scoped bet with a time budget. I design the solution to fit that budget, name the risks, and say what's out of scope before anyone writes code. The outcome: bad bets die on paper, where they cost a conversation instead of a build cycle.

How I make it work for real people

Design for behaviour

A feature only matters if someone actually uses it. I find the real trigger, cut the friction between the person and the payoff, and make the behaviour easier before trying to make it more motivating. The outcome is a feature people come back to without being nudged. If a pattern lifts a metric by making someone feel worse, it doesn't ship.

How I know it worked

Prove it

The outcome I'm after is what changed for the person using it, so before building I write down what would show it worked: an early signal like activation, and the slower outcome behind it like retention. After it ships, I go back and check. Most work never gets that second look. I make it a step.

How I make it durable

Ship it as a system

Accessible markup, motion with a reason, and nothing hard-coded: a component asks for a colour or a size by name, and one shared file answers. Those named values are design tokens. Colour and spacing can't drift, because there is nowhere for them to drift to. The outcome: change stays cheap — a rebrand is one file. This site is built that way (see the case study).

In practice

This site re-skins itself from one line of CSS.

The clearest example of the method is this site itself, because the method was used to build it.

Problem & budget

Re-theming the portfolio for each company meant hand-editing CSS on every page: slow, and easy to get inconsistent. Worth one focused cycle.

The one rule

Nothing in the markup is allowed to name a colour. A component asks for a role — the accent, the page background — and whichever brand file is loaded answers. Those roles are semantic tokens. The industry name for encoding intent this way is a steering layer: design intent encoded where neither a person nor an AI agent can drift from it. No framework, no build step either: plain HTML and CSS.

Build

Three stylesheets load in order. One lists every value a component may ask for and gives each a neutral default. One overrides those values for a single brand. One holds the components, which name values but never set them. In that order they are the token contract, a swappable brand pack, and the components. Accessibility defaults sit in the contract, so every component inherits them.

Outcome

Re-theming went from edits on every page to one line in each page's <head>. The site also ships structured data and an llms.txt index, so an AI assistant can read the system as easily as a browser can.
