Telling the backend how to read

Full plan: handoff-bindings-scenario-derived-331.md

What we're building and why

Today the design pack describes what each record looks like, but not which records a screen shows, on which made-up date, or how “overdue” is worked out. After this ticket, the pack states all three, and a check fails if they stop matching the real files.

The concepts this plan rests on

A binding: which list shows which records

A binding is a short note saying “this part of the screen shows these records, filtered and sorted like this.” It names a record shape, never a web address (an endpoint), so the backend keeps its own URLs.

today view   ← care-tasks
  filter: not done, and due or overdue
  order:  as served
  witness: task-03, task-05, task-08, task-18

The witness lists the exact records the page shows today. That lets a browser test prove the written rule matches the real page.

A scenario constant: the fixed “today”

The demo lives on a frozen date, 14 July 2026, so its sample data never goes stale. That date was hidden in a brief, and an engineer guessed the 15th, which put every status a day off. Now it ships as data in scenario.json.

A derived field: computed, never typed in

A derived field is worked out from other fields. A task's status comes from its due date and today. Marking it readOnly (the server sets it, the client never sends it) plus a written rule tells the backend to compute it.

"status": { "readOnly": true,
  "x-derived": { "from": ["due", "done", "../scenario.json#/today"],
                 "rule": "done → ok; before today → overdue; …" } }

A check that can fail

The build gate compares the pack against its sources. Every check is also tested with a deliberately broken input (a mutation), to prove it would actually go red.

The plan at a glance

  • Phase 1: write the bindings statement and mark the two status fields as derived.
  • Phase 2 (after 1): the generator projects them into the pack and refuses anything broken.
  • Phase 3 (after 2): regenerate the pack, extend the gate, update the docs.
  • Phase 4 (after 3): run every gate and fill in the question-to-line table.

  • Everything in the pack is generated, and the drift check (rerun every generator, fail if any output changed) stays clean.
  • The gate checks bindings, today and derived fields, each against a mutation.
  • The PR maps seven seam-run questions to a file and line.
  • No URLs, caching, paging or auth enter the pack.
  • The real page, opened in three browsers, shows exactly the records each binding's witness lists.
