Four owner decisions, one sitting

Full plan: .claude/plans/discovery-owner-decisions-507.md

What we're building and why

Six follow-up tickets are stuck. Each one is waiting on a choice that only the owner can make. This sitting records four of those choices in the owner's own words, so that each ticket can start knowing the answer it is built on.

The concepts this plan rests on

1. A page computed from a log

The PRD page (the product requirements document) starts life projected: generated from a log of recorded answers, not typed. The log works like a bank statement, which prints every line from the transactions and never makes one up. D-c decides which new blocks the page may show.

2. A table that decides what the agent is told

SECTIONS is the page's list of sections. Some rows also feed the interviewing agent's instructions, and changing those instructions changes the agent's stamp, a fingerprint of its prompt. We measured which rows feed it. Only "ladder" rows do (sections chosen by the decision's level), so a new summary-style row leaves the stamp unchanged.

ladder row added      → stamp changes   (tested)
summary row added     → stamp unchanged (tested)

3. A strict form, and old forms that cannot be refilled

Each op (one recorded action, like "record a decision") must have exactly its listed fields. A new field would make every old record fail. D-b picks a fix: mark the field optional for old records, or rewrite them. Rewriting breaks the rule that records are never edited.

4. A question budget

Full discovery asks about 30 questions. One number caps the total. Below 34, any three topic modules overflow it, and that overflow is intended. D-a decides where new metric questions go, and that choice sets the number.

12 core + 4 quality + 2 metrics + 15 (two modules) = 33 ≤ cap

How the pieces fit

Brief: options marked (agent)→ Owner types four lines→ Quoted on #507→ Six tickets point to their decision→ Wave 3 tickets plan their changes
