Saved groups on the build canvas

The full plan: compose-and-name-groups-315.md

What we're building and why

Today every screen on the canvas is built part by part, so a header shared by five screens is five separate copies. After this, the owner saves a few parts as a named group, places copies of it anywhere, and can promote it to a real component.

The concepts this rests on

1. Definition and instances

A definition is the master copy; an instance is a placed copy that points back to it. Change the master and every copy changes. This plan needs it so a shared header is designed once.

group g1 "app-header"  → title · help button · icon
screen A: [copy g1-1]   screen B: [copy g1-2]

2. Overrides

An override is a short note on one copy saying "same as the master, except this". It works like a sticky note on a photocopy. One copy's title can say "Add a payee" while the master still says "Home".

g1-2 overrides: { set: { header: { title: "Add a payee" } } }

3. The ledger (append-only record)

Every change is a new line in a log file, and lines are never edited or removed. The group file on disk is recomputed from that log, so the two can never disagree.

ops.jsonl      ← the truth, one line per change
groups/g1.json ← rewritten from it on every save

4. Promotion as admission

Admission is how a new part joins the official component library. Promote sends a group through the same door an imported design uses, and the owner still approves it. One door means one set of checks.

How the pieces fit

Tick parts, name them→ Definition in the ledger→ Place copies + overrides→ Screen renders expanded copies→ Promote → proposal→ Owner ratifies

The plan at a glance

  • Grammar: two new change types and the copy expansion.
  • Storage (after grammar): write and check groups/.
  • Promote + ratify (after storage): the proposal and its provenance line.
  • Page (after promote): tick, place, override, promote.
  • Handoff count (after grammar only): groups vs admissions.
  • Checks, journey, docs (last).
system/canvas-ops.mjs            # the two new changes, copies expanded
portal/lib/canvas-store.mjs      # writes groups/<id>.json
portal/lib/promote.mjs           # new: group → proposal folder
portal/lib/ratify.mjs            # "composed in run X"
portal/public/canvas-groups.mjs  # new: the owner's controls
agent-layer/gen-build-handoff.mjs# prints the count
tooling/build-checks.mjs         # the proofs
tooling/canvas-journey.mjs       # the browser walk-through
  • Save, place twice, edit master, override one copy, blocked delete — all proven.
  • A browser walk-through ends with a proposal folder whose source is the group.
  • The handoff's group-vs-admission count is checked on a fixture.
  • A promoted group is approved all the way into the component library, with every check green.
  • Saving and placing never write to the design system; only Promote writes a proposal.
