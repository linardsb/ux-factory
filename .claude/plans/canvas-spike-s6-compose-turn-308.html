S6: the compose turn

Brief for canvas-spike-s6-compose-turn-308.md, which is the source of truth.

What we're building and why

Nobody knows yet whether an AI asked for one screen stops after one screen or designs the whole app at once. This spike runs it on a real banking PRD (the product requirements document a discovery session produced) and records what it does before the loop is built.

The concepts this plan rests on

One turn, one screen, then wait

The AI proposes a single screen and stops so the owner can accept or refuse it. If it rushes ahead, the owner loses control of the design. That is the risk being tested.

turn 1 → propose "add payee"  → wait for owner
turn 2 → propose "check name" → wait for owner

Resuming a conversation

Each turn picks up the same AI conversation instead of starting a new one. This is called resume (continuing a saved session by its id). The spike checks that the id stays the same across turns, or the test means nothing.

A tool that checks before it records

The AI can only act by calling one tool, screen_compose. The tool checks the screen uses only known parts, then records it. It records in memory only: nothing real is saved. This is a dry run.

AI calls tool → parts all known? → yes: record "proposed"
                                 → no:  send the error back

Grading by rule

A small function reads each turn's log and labels it: clean, ran ahead, or stopped with nothing. It is tested on fake logs first, so it has been seen to catch a runaway before any money is spent.

How the pieces fit

Banking PRD + parts list→ AI turn (resumed)→ checking tool→ turn log→ grader→ verdict posted

The plan at a glance

  • Phase 1: start a separate working copy, make the spike folder.
  • Phase 2: write the driver; prove the grader and the tool for free. Needs phase 1.
  • Phase 3: paid run 1; runs 2 and 3 only if the AI ran ahead (run 3 also needs the owner's answer). Needs phase 2 green.
  • Phase 4: README, comment on the parent issue, pull request. Needs phase 3.
