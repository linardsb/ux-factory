Run 1: Faster Payment on the canvas

Full plan: faster-payment-build-run-316.md

What we're building and why

Every piece of the canvas exists, but nobody has built a real flow with it yet. After this, a four-screen payment flow sits on the canvas: the agent proposed it, the owner decided every step, and one part came from a real design import.

The concepts this rests on

A ledger, not a picture

The canvas is saved as a list of actions, not a drawing. That list is an append-only log (lines are added, never changed). Each line says who did it: owner or agent. This build needs it because the run's honesty claim is "every screen traces to a recorded line".

7  agent  compose "confirm-payee"   proposed
8  owner  accept 7
9  agent  add state "close-match"   proposed

Screens declare their states

A screen needs more than its happy version: loading, error, empty. A payment check also has "close match" and "unavailable". Today only five fixed states are allowed. So a screen will list its own extra states when it is made, and the checker will then ask for each one.

A check that allows the agent, but only with a receipt

A test currently fails if any saved line says "agent", because no agent had ever run. Now one will. The new rule: an agent line is fine only if the session transcript (the run's log of what the agent did) has the matching entry.

Where each part came from

Each piece on a screen gets a derived label: imported, admitted, composed or stock. Nothing stores the label. It is worked out from the log each time, like a bank balance computed from the transactions. The run must show at least one "imported".
