#338 — run 0: the owner's next real product, in the UI

A five-minute briefing. This one is unusual: the plan builds no code. It runs a session and reports what it showed. Full plan: .claude/plans/discovery-run-0-338.md

The one thing that matters. The 30 answers are the measurement, and they must be the owner's own words about the owner's own product. An agent that writes them has fabricated the experiment and destroyed the ticket. Phase A is the agent's, Phase B is the owner's alone, Phase C is the agent reading files and transcribing dictation.

1. What we're doing, and why

Epic #279 built a discovery half — a question bank, an op grammar, a session spine, a PRD projection — and staked itself on one falsifiable claim: that the owner's next real discovery session would start in the portal rather than the terminal. Every artifact built so far is fictional or an in-memory test fixture. Nothing has ever carried a real product through.

This ticket is that session. It is deliberately not one of the measured runs (#291 scores against a sealed key; #292 fires the AI module against a fixture). It has a second job too: five tickets were deferred on reasoning alone, and running without them is the only way to find out whether the reasoning held.

2. The four concepts this rests on

Concept 1 — a falsifiable hypothesis has a WRONG condition, and you must be able to reach it

The epic says: right if the next real session starts in the UI and reaches a PRD in one sitting; wrong if the owner opens a terminal and types /think instead. The terminal is deliberately left installed and unmodified — it is the control. Deleting it would let the UI win by having no alternative, which measures nothing.

Why this plan needs it: it is why AC3 asks for the owner's honest recollection rather than a metric, and why a WRONG verdict is recorded as a finding rather than treated as a failure to fix.

The trap. An experiment whose wrong condition cannot be reached is not an experiment. The plan makes WRONG explicitly acceptable so nobody is quietly incentivised to report RIGHT.

Concept 2 — pre-registration: fix the counters before you look

Deciding, after a long afternoon, whether five deferred tickets "hurt" produces opinion with a number attached. Pre-registration means writing down — before the sitting — exactly what observation would count as evidence for each one, and where in the package it would be read from.

write the counters→ run the sitting→ read the counters |never: run → invent a counter that fits

Analogy: calling your shot in pool. Naming the pocket first is what makes the shot mean something. Where it breaks: in pool you either sink it or you don't; here "no evidence either way" is a legitimate third outcome, and is itself the finding that the deferral was safe.

Why this plan needs it: AC4 is the ticket's second deliverable, and it is the half most likely to decay into vibes. Tables 1 and 2 in the plan are the pre-registration.

Concept 3 — provenance decides where the data lives (R1)

The run package's run.json carries a provenance field, and it is not a label — it is a routing decision made in code:

provenance: fictional→ discovery/<slug>/ — committed, public
provenance: real→ $JOBS_DIR/_discovery/<slug>/ — never committed

This repo is public and inspectable. The owner's unreleased product must not enter it. That is why run 0 is real, why AC6 exists, and why the plan carries a script that scans the finished report for any eight-word span lifted verbatim from an answer.

Why this plan needs it: the single highest-consequence mistake available in this ticket is picking fictional in the drawer. The plan makes the operator read the note under the dropdown before pressing Start.

Concept 4 — the package is the evidence; memory is not

Every AC5 number is read from a named field, never recalled. A session leaves four things behind:

Phase A proves this whole chain on one throwaway turn. Phase B runs it 30 times. Phase C reads what it left behind.

F1 — the gap this run will expose. The projection is CLI-only; #290's PR says so outright. The session is entirely in the UI, but the PRD needs one terminal command afterwards. The plan takes the plain reading of AC1 and does not build a route — patching the gap before the run would mean run 0 no longer measures the thing as built. It logs a named finding instead, and that finding matters: the epic's secondary user, a guest with no terminal, cannot finish the workflow at all today.

Phase B — the sitting

Drawer settings, all verified against run.json afterwards rather than trusted: depth full-discovery (30 questions — observed unique, no nulls), provenance real, entry blank-idea, posture Think, branch null. Keep a running note of five things while answering — one per deferred ticket. They are the AC4 evidence and they are not recoverable from the package afterwards.

Acceptance criteria

  • AC1 real session, started and finished in the UI — verified from run.json, not memory
  • AC2 a generated prd.md in one sitting
  • AC3 the hypothesis in the owner's quoted words — WRONG is a finding, not a failure
  • AC4 a verdict on #283 · #285 · #286 · #287 · #289 — hurt / did not / no evidence either way
  • AC5 answered · abandoned · banked turns · SDK turns · latency · cost (or tokens) · wall-clock
  • AC6 nothing from the package committed — three checks, one of them a verbatim-span scan
What no gate here can reach. build-checks groups 29–31 drive the discovery modules over in-memory fixtures. Nothing in the gate stack reads a run package on disk — deliberately, because a directory on disk could be mistaken for a real one. So no green run proves this session happened, that a human answered it, or that the report is honest. The pre-registration and the three safety checks are what stand in for a gate, and the report says so rather than listing 31 green groups as if they covered it.
