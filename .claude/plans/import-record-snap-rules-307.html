The import record and the snap rules

Plan: import-record-snap-rules-307.md

What we're building and why

Today an import from a design tool leaves no trace of what it lost or whether it looks right. After this, every import writes a record that states both, and raw values get matched to our tokens in the open.

The concepts this plan rests on

A record that cannot lie

Some fields are worked out from the data, never typed in. A checker recomputes them and refuses the file if they disagree. It is like a receipt whose total is recalculated at the till.

drops   = everything the import lost   (derived)
verdict = red | green | missing        (derived)
no measurement → "missing", never "green"

Wrong but green

Contrast checks (WCAG, the legibility rules) can all pass while the colours are plainly wrong. So we compare the average colour of the text in each part against the source picture. The difference is ΔE (a standard "how different do these colours look" number).

ΔE ≥ 5.0 in any part → red, even at 12/12 WCAG

Snapping by nearest value

A design drawn with raw numbers (say, 14px) gets matched to the closest token (a named design value, like caption = 13px). Only an exact match is accepted without asking.

exact  → accepted silently
near   → shown as a proposal for the owner
far    → dropped, and listed as lost

Fixes remembered by fingerprint

A hash (a short fingerprint computed from a file's bytes) names each source file. The owner's corrections are saved under it, so importing the same file again reuses them. A changed file gets a new fingerprint and starts clean.
