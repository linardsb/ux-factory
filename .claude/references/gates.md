# The gate stack — what each gate owns, and what it states it cannot reach

Load this when adding a gate, changing one, or working out why a green run proves less than it looks like it does. Per-module invariants are NOT here — they live in each module's own file header, which is what an editor sees. This file holds only what no single file owns: which gate covers what, and where each one's coverage stops.

**The convention that makes the stack readable:** every gate STATES the boundary it cannot reach, and names the gate that owns the other side. Groups 9, 11, 13, 16, 18, 19, 23, 24, 25, 26, 27, 28 and 34 each carry that sentence, and so do the journey drivers. A gate that claims total coverage is the one to distrust — see [[the check that cannot fail]]: every #137 defect survived a green gate the same way, by skipping the thing it tested. Mutate the source; run the function, don't grep it.

**What runs in CI (`verify` workflow):** `build-checks.mjs`, the generator drift checks and token-lint (`verify` job); the visual-regression gate (`visual` job); the CodeQL gate (`codeql` job); the dependency-advisory delta (`audit` job); and `gates-green`, the one check that is green only when all four were. **Everything else is operator-run** — the journey drivers, `vt-verify`, `vt-stack-audit` — and is not a merge blocker.

**Reading a red leg (#416).** The verdict is the driver's OWN last line — `<driver> ✓ …` or `<driver> ✗ N assertion(s) failed` — and the per-engine `── <engine>: N passed, M failed` above it. **Never a wrapper's exit status:** `node tooling/<driver>.mjs all | tail -30` reports `tail`'s status, so a red run reads as exit 0, and #416 lost a result to exactly that. ## The security gate — the merge gate, CodeQL, and the advisory delta

Three CI jobs plus branch protection on `main` (#387), together making one guarantee: **a pull request cannot merge except through a step that has no model in it.** Nothing an agent does can put code on `main`; the four gates must be green and `gates-green` is the required check that says so.

- **`gates-green`** (`.github/workflows/verify.yml`) — refuses unless `verify`, `visual`, `codeql` and `audit` all report success **and** the visual gate's true step outcome does too. It writes nothing and holds no credential. **Branch protection requires THIS check, not `visual` directly**, because it is the one check that covers all four jobs at once, and because a `feature/v3-*` branch launders the `visual` failure that reaches this job — see the first cannot-reach below.
- **`codeql`** — GitHub's own static analysis over a `javascript-typescript` database, scoped by `.github/codeql/codeql-config.yml`, plus a step of ours that reads the resulting alerts through the code-scanning API in TWO LEGS (#408): the PR's own merge ref, and `refs/heads/main`. Both run, both print, either one reds the job.
- **`audit`** — `tooling/audit-delta.mjs`, the npm advisory DELTA between the PR's base SHA and its head, across every discovered lockfile directory.

**What they cannot reach:**

- **An AGGREGATOR job cannot see a job-level `continue-on-error`.** `needs.<job>.result` reports `success` for a laundered failure and `needs` exposes no second field with the truth ([actions/toolkit#1739](https://github.com/actions/toolkit/issues/1739)), so a downstream job must read the true outcome from the job's own output. That is why `visual` publishes its VR step's real outcome as a job output and `gates-green` checks both. **The laundering stops at the workflow boundary:** the job's own CHECK RUN still reports failure — measured at #387 on the deleted-baseline head `343022a`, where `needs.visual.result` was `success` while the jobs API and the check-runs API both said `visual` → `failure`. So this is not a hole in branch protection; it is a hole in any aggregator that trusts `needs.<job>.result`. Protection requires `gates-green` because it is the one check covering all four jobs, not because requiring `visual` would have been unsafe. **Standing rule, stated here because no gate enforces it:** any future job carrying that flag must publish the same output and be checked the same way, or it walks straight past `gates-green`. `verify.yml` carries exactly one such job today — the D11 VR freeze.
- **A SKIPPED check counts as PASSING for branch protection.** So `gates-green`'s `if:` may never narrow past `!cancelled() && github.event_name == 'pull_request'`. Any condition that can be false on a real PR — a path filter, a draft check, a branch name — is a hole straight through the gate, and it looks like a green check while it is open. The same trap applies to `audit`, whose `if:` is true for every pull request by construction.
- **The merge-ref read is DIFF-SCOPED, which is exactly why the gate reads `main` as well (#408).** The step's FIRST leg queries `state=open` on `refs/pull/N/merge`, which reads like "every open alert" and is not one: GitHub shows an alert on a pull request only when **all** the lines of code it identifies are in that PR's diff ([About code scanning alerts](https://docs.github.com/en/code-security/code-scanning/managing-code-scanning-alerts/about-code-scanning-alerts)). **Measured at #400:** PR #394 was based on the exact `main` commit carrying fourteen open high alerts, both of its merge-ref analyses returned zero, the gate printed green and it merged; the job log says `Computing PR diff ranges… Persisted 33 diff range(s) across 15 file(s)`, against `Not performing diff-informed analysis` on the push-to-`main` run. So that leg answers **which alerts this PR's own diff raises**, and nothing else — a real guarantee, but not the one #387 was written to make. The SECOND leg closes it: it reads `state=open` on `refs/heads/main`, whose push analysis is the full-tree one, and fails on a high or critical there too, with a different error line because "your PR raised this" and "`main` already carries this" need different fixes. **Rely on the display rule, not the mechanism** — whether every query participates in diff-informed analysis is documented nowhere, so the display rule is what leg 1 guarantees and the job log is only corroboration; leg 2 does not depend on it at all, because a branch ref carries no PR diff to inform anything. This file, `CLAUDE.md` and `verify.yml` asserted the whole-tree reading of leg 1 until #400, having read the query shape as the guarantee; #408 made that reading TRUE by adding leg 2 rather than by re-reading leg 1. **`audit` beside it is a base-vs-head DELTA and this is deliberately not symmetric with it** — `audit` reports what the PR brought, `codeql` reports what the PR brought *and* what `main` still carries — which is the trade #408 chose on purpose. **Two consequences.** A genuine false positive that lands on `main` IS a standing merge block, on every open PR at once; #388 forbids dismissing it in the Security tab, so the routes are an honest code change that stops the query matching, or a decision to change #388's policy. And **the local CodeQL bundle is a superset of leg 1 and the exact shape of leg 2** — it scans the whole tree with no diff ranges, so a local zero is stronger than leg 1 needs and is sufficient, a local red does not predict a red leg 1, and it is the right oracle for leg 2: #395's byte-equal parity (same rules, paths and line numbers) was measured against `refs/heads/main`'s PUSH analysis, which is precisely what leg 2 reads. Use it with `--codescanning-config=.github/codeql/codeql-config.yml`, as `piv-fix-review-findings` does, and scope a finding to the PR's own diff before deciding which leg will fire on it.
- **Protection is `strict: false`, so a PR is not re-tested against a `main` that moved.** Both new gates are computed at push time — CodeQL analyses `refs/pull/N/merge` as it was then, and the delta is against `github.event.pull_request.base.sha` — so a PR can merge carrying code neither gate has seen against the current base. Deliberate: `strict: true` re-queues every open PR on every merge, which on a solo repo is a tax that buys little. Flip it the day two PRs are routinely open at once.
- **The required contexts are CASE-SENSITIVE, and this repo carries two checks whose names differ only in case.** Our job is `codeql` (`github-actions`); GitHub Advanced Security publishes its own results check as `CodeQL`. Typing the wrong one into the protection call requires a check that is not this gate — and since the call is made by hand, once, with nothing gating it, the typo would sit there looking configured. Verify with `gh api repos/linardsb/ux-factory/commits/<sha>/check-runs --jq '.check_runs[].name'` after setting it.
- **`enforce_admins` is OFF, deliberately.** The owner can merge past a red gate; nobody else can, and no agent can. The guarantee is about what a model can put on `main`, not about locking the owner out of their own repo on a flaky run. Turning it on is one API call if that trade ever changes.
- **Protection gates the MERGE, not the review.** A PR can be opened, marked ready and reviewed while red. `piv-create-pr` opens PRs ready for review, as it always did — the draft-flip design that would have changed that is not possible here (next bullet).
- **The draft flip is impossible with the Actions token, and that is why this is a merge gate.** `markPullRequestReadyForReview` answers `FORBIDDEN — Resource not accessible by integration` to `GITHUB_TOKEN` even with `pull-requests: write` in the job's own token block, and REST's `PATCH /pulls/{n}` has no `draft` field, so GraphQL is the only route at all. Measured at #387 three ways — via `gh pr ready`, via the mutation directly, and again with the repo's `can_approve_pull_request_reviews` set to `true`, which is **not** the cause. Doing it would need a PAT held in a repo secret; branch protection needs no credential and gates the stronger thing.
- **CodeQL's scope stops at the allowlist, and nothing gates the allowlist.** `paths` in `.github/codeql/codeql-config.yml` is hand-maintained: a new top-level source directory is **silently unanalyzed** until someone adds it, and the gate stays green while covering less. It self-maintains for a new root page (`*.html`), for a new module at `discovery/`'s or `scenarios/`'s own root, and for anything inside the six listed directories, and nowhere else. **The list is complete as of PR #391 and nothing keeps it that way.** The completeness check is by hand — list every tracked file the `javascript-typescript` extractor takes **that can carry code** (`*.mjs` `*.js` `*.cjs` `*.jsx` `*.ts` `*.tsx` `*.html`) against the allowlist — and it found two files outside it: `scenarios/validate.mjs` (332 lines, imported by `tooling/drift-check.mjs` and `agent-layer/gen-company-package.mjs`, both in scope, and CodeQL cannot follow a call into an out-of-scope callee) and `scenarios/check.html` (106 tracked lines carrying a `<script>`). **Run it at that width or it lies:** the first pass listed only `*.mjs`/`*.js` and missed the page. And the extraction log cannot audit this — an out-of-scope file never appears in it, so a green job covering less looks identical to a green job covering everything. **The extractor also takes `.json`** (28 extracted at `4be4b72`, all already inside allowlisted directories); it is left out of the check deliberately, because JSON is data and the default suite has no query that fires on it — say so rather than dropping it silently, or the next person re-deriving the list will read the omission as an oversight. An omission is a live blind spot the moment it happens, not a future one. Re-run the check, at that width, whenever a root directory appears. `.github/workflows/` is deliberately outside it, so CodeQL's own GitHub Actions queries never run on this workflow. `handoff/`, `traces/`, `replay/`, `discovery/<slug>/` and `proto/compositions/` are excluded because a finding on a generated file belongs to its generator, and a finding on a committed agent run cannot be fixed without hand-editing it, which the honesty contract forbids. **The exclusions are globs, and CodeQL's `**` matches ZERO or more segments** — measured at #387, a `discovery/*/**` ignore collapsed to `discovery/*` and silently took the four real modules with it, with the gate still green. An ignore that removes a subtree of an allowlisted directory has to be verified against the job's own extraction log, not read.
- **CodeQL uploads; it does not block.** `github/codeql-action/analyze` has no fail-on-findings input, so the job goes green on findings and the gate is a step we wrote that reads the alerts back. Delete that step and CodeQL keeps running, the Security tab keeps filling, and nothing holds a PR — a gate that looks alive and is not.
- **An open high or critical alert on `main` blocks EVERY pull request, and the fix belongs on `main` (#408).** The push-to-`main` analysis is the full-tree one and is what finds it; leg 2 reads it, so the day `main` acquires one, every open PR goes red at once printing `main already carries N blocking alert(s) — NOT this PR's doing`. That is the point, not a side effect: the promise "`main` carries nothing high" is a different promise from "this PR raised nothing high", and only the first survives an alert nobody happens to touch. **What it costs, stated so nobody rediscovers it as a bug.** The block lands on whichever PR is open rather than on the change that caused it, which is why the error line names the remedy — clearing it on `main` clears every PR at once. **And the PR that clears it cannot go green.** Leg 2 reads `refs/heads/main`'s push analysis, which does not move until the fix MERGES, so the one PR whose whole purpose is removing the alert sits red on leg 2 until it lands — leg 1 goes green (its diff covers those lines and the alert is gone) and leg 2 does not. That is not a defect to re-file; it is what this shape costs. **The sanctioned route is to merge that PR past its own red leg 2**, with leg 1's green as the evidence the fix works, and `enforce_admins: false` three bullets up is what keeps that possible the day protection goes on. Say so in the PR body; a red check merged without a stated reason is indistinguishable from one merged by mistake. **Branch protection on `main` is OFF** (verified 2026-09-14: `branches/main/protection` → 404, `rulesets` → `[]`), so today this is a red check the owner can merge past, not a mechanical block; it becomes one the day protection goes on, and that sequencing was known when #408 was decided. It landed on a `main` carrying **0** open alerts of any severity and with no PR open (both verified 2026-09-14), so it stalled nothing. **Three things leg 2 cannot reach.** It reads `main`'s LAST COMPLETED push analysis, so between a merge and that run finishing it judges the previous tip. Its ref is the literal `refs/heads/main`, not `base.ref`, so a PR based on a feature branch is still judged against `main` — deliberate, because no other branch gets a push analysis and the alternative is the positive control failing the gate for a missing scan. And it inherits the allowlist blind spot two bullets above: an alert CodeQL never looked for on `main` is not an alert leg 2 can read.
- **The threshold is `high` + `critical`.** `medium`, `low` and unrated alerts are raised and readable in the Security tab; they do not block the merge. #388's remediation loop has landed, so a red gate now has a route through it: `piv-fix-review-findings` takes a PR number, reads the blocking alerts off the merge ref (leg 1, the diff-scoped read — the two bullets above) and fixes them in code without suppression. It does NOT route leg 2: an alert `main` carries is fixed by a PR whose diff covers those lines, which is a separate change on `main`, not a fix inside whichever PR the leg reddened. The threshold is unchanged — widening it to everything is a separate decision, not a consequence of the loop existing.
- **What CodeQL plus an advisory delta does not cover:** `portal/lib/origin.mjs`'s CSRF logic, the Worker's routes, and the honesty-contract invariants. Those stay with `build-checks` and human review.
- **The advisory delta is a delta.** The pre-existing `tooling/style-dictionary` advisories — five at PR #391, and a live number that moves as advisories are published — do not block and are not tracked here; only an advisory ID the base did not carry does. It cannot see an advisory published after the PR merges.
- **Fork PRs cannot pass.** A fork's token is `security-events: read`, so the SARIF upload fails, the `codeql` job fails, `gates-green` refuses and the PR cannot merge. No forks today, and no workaround should be added without first deciding what a fork's analysis is allowed to see.
- **No secret, anywhere in this gate.** CodeQL needs no account and no configuration outside this repo; `gates-green` holds no credential. The one human step is enabling branch protection on `main` — a single API call, and without it every gate still runs and reports while nothing mechanically blocks a merge.

## What no gate can see

Stated so it is not rediscovered as a bug:

- **A deleted mount can orphan its CSS.** A re-scoped transition block is dead if the deleted module armed its class; nothing here detects it (PR #261).
- **A guard's WIRING**, as opposed to its predicate — groups 9 and 11 both live with this.
- **The screen-reader pass** and the judgement-level a11y items (labels that say what they do, empty state as invitation, colour never the only signal). Axe and Lighthouse are absent; axe belongs in the VR tool light and dark, Lighthouse stays operator-run because it is machine-dependent theatre.
- **Whether a green gate tested anything at all.** The recurring defect shape in this repo: the check skipped the thing it tested. Mutate the source; run the function, don't grep it.
